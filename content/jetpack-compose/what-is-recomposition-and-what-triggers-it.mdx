<ShortAnswer>

**Recomposition is Compose re-running composable code because the UI it describes may need to change.**

A common trigger is observable state that was read by that UI changing. Compose tracks those reads, so it knows which parts of the Composition depend on that state and where work may need to run again. A composable can also run again when its caller recomposes and gives it different inputs.

The important mental model is that Compose doesn't blindly rebuild the whole screen. **Recomposition follows dependencies.**

</ShortAnswer>

## What the interviewer is testing

This question isn't really about knowing that "state changes trigger recomposition."

The interviewer wants to know whether you understand **how Compose connects state to the UI that depends on it**.

If a composable reads observable state, that read creates a dependency Compose can track. When the value changes, Compose knows where the existing Composition may now be out of date and can schedule the relevant work again.

A strong answer explains that relationship before talking about performance, stability, or runtime internals.

## ❌ Common mistake

<CommonMistake>

> "Whenever state changes, Compose recomposes the whole screen."

That's the wrong mental model.

Compose tracks where observable state is read. If one value changes, the UI that depends on that value may need to run again; unrelated work does not automatically need rebuilding.

Also avoid treating every recomposition as a performance problem. Recomposition is how Compose keeps the UI synchronized with state. The problem is expensive or unnecessary work inside code that may run again.

</CommonMistake>

## If they ask you to elaborate

Imagine the same order screen from the previous question.

The screen shows the order itself and a cart badge:

```kotlin
@Composable
fun OrderScreen(
    order: OrderUiModel,
    cartCount: Int,
) {
    OrderDetails(order)
    CartBadge(cartCount)
}
```

Now the user adds another item to the cart.

The order has not changed. The cart count has.

If the observable state behind `cartCount` changes, Compose knows that the UI reading that value may now describe something different. That work can be scheduled again without treating the entire screen as brand new.

That's the useful way to reason about recomposition:

- **State is read by UI.**
- That read creates a dependency Compose can track.
- When the value changes, the dependent UI may need to run again.

A composable can also be called again because its parent recomposes and passes different parameters. So "recomposition follows state reads" is a useful shortcut, but the deeper idea is **dependency tracking**.

<Remember>

**When you're asking why something recomposed, follow the dependency back to the state it reads.**

</Remember>

That leads naturally to the next question: if state drives these UI updates, **what exactly counts as state in Compose, and how does it drive the UI?**

## Production thinking

This starts to matter when a screen has several independent pieces of state.

An order screen might be refreshing data while a cart badge changes, a dialog opens, and an error banner appears. If every part of the screen depends on one large blob of state, it becomes harder to see what actually depends on what.

Good Compose code keeps those dependencies clear. Give each piece of UI the state it needs, keep business logic and I/O outside composable bodies, and make work that may run again cheap.

I wouldn't start by trying to "stop recomposition." First make the state model and ownership clear. If there is still a measured performance problem, then stability and recomposition tooling become useful follow-ups.

## What separates a senior answer

<SeniorAnswer>

- Defines recomposition as re-running composable work to update an existing Composition, not recreating the screen from scratch.
- Explains the trigger through **dependencies**, especially observable state read by the UI.
- Knows a composable can also run again when its caller recomposes and supplies different inputs.
- Doesn't confuse recomposition with redrawing the entire screen.
- Treats recomposition as normal framework behaviour rather than something to eliminate.
- Keeps expensive work, I/O, and business logic out of composable bodies because that code may execute again.
- Starts with state ownership and clear boundaries before reaching for stability or recomposition optimisations.
- Stops before turning the answer into a discussion of snapshots, SlotTable, compiler behaviour, or phase-specific invalidation.

</SeniorAnswer>

## Key takeaways

<KeyTakeaways>

- Recomposition re-runs composable work when the UI it describes may need to change.
- Observable state reads create dependencies Compose can track.
- When that state changes, the UI that depends on it may be scheduled to run again.
- A composable can also run again when its caller provides different inputs.
- Recomposition follows dependencies; it does not mean rebuilding the whole screen.
- In production, keep state boundaries clear and composable work cheap rather than trying to eliminate recomposition.

</KeyTakeaways>
