<ShortAnswer>

The biggest difference is **who keeps the UI in sync with state**.

With the View system, you usually get hold of existing View objects and update them when state changes—set the text, show or hide something, update the adapter, and so on.

With Compose, you describe what the screen should look like for the state you have now. When that state changes, Compose updates the UI that depends on it.

That's the useful meaning behind **imperative versus declarative UI**. It's not really XML versus Kotlin; it's a change in who is responsible for turning state changes into UI changes.

</ShortAnswer>

## What the interviewer is testing

This question sounds like it's comparing two UI toolkits, but that's rarely what the interviewer cares about.

They're looking for whether you understand the shift from manually updating the UI to describing it from state. If your answer focuses on XML versus Kotlin or Views versus composables, you've probably missed the engineering decision behind Compose.

A strong answer explains the change in responsibility first. The terminology comes afterwards.

## ❌ Common mistake

<CommonMistake>

"Views are imperative and Compose is declarative."

That's the label, but it doesn't explain the difference.

Also avoid making it about XML versus Kotlin. You can build View-based UI in code, and Compose being Kotlin-first isn't the important engineering shift here.

The useful question is: **when the state changes, who is responsible for making the screen match it?**

</CommonMistake>

## If they ask you to elaborate

Imagine an order screen that can be loading, showing an order, or showing an error.

With the View system, you might receive a new state and then update several existing Views:

```kotlin
progressBar.isVisible = state.isLoading
contentGroup.isVisible = state.order != null
errorView.isVisible = state.error != null
ordersAdapter.submitList(state.items)
```

There's nothing inherently wrong with that. The important point is that **your code is coordinating those mutations**.

As the screen grows, there are more things to keep synchronized. If one update is forgotten, the View hierarchy can end up showing a combination that doesn't match the application's actual state.

Compose approaches the same problem from the other direction. Instead of describing how to move the old UI into the new state, you describe the UI for the state you have now:

```kotlin
when (state) {
    OrderUiState.Loading -> LoadingScreen()
    is OrderUiState.Content -> OrderScreen(state.order)
    is OrderUiState.Error -> ErrorScreen(state.message)
}
```

Now the code says what each state looks like. Compose takes responsibility for updating the UI when that state changes.

That's why declarative UI becomes easier to reason about on state-heavy screens: **state is the input, UI is the result**.

<Remember>

**With Views, you update the UI. With Compose, you describe the UI and Compose updates it for you.**

</Remember>

This doesn't mean Compose redraws the whole screen every time something changes. How Compose keeps track of the UI, and how it decides what work needs to run again, are separate questions. Those are where **Composition** and **recomposition** come in.

## Production thinking

The difference becomes much more valuable as a screen grows.

A simple login screen only has a few pieces of state. A production screen might have loading, cached data, pull-to-refresh, dialogs, permissions, paging, connectivity changes, and navigation events happening at the same time.

In a View-based screen, your code often coordinates multiple UI updates to keep everything synchronized. In Compose, you describe what the screen should look like for the current state, which makes complex screens easier to reason about.

Compose doesn't decide where that state comes from. That's still the job of your architecture. Views and Compose can even coexist in the same application—the rendering toolkit doesn't change who owns application state.

## What separates a senior answer

<SeniorAnswer>

- Starts by explaining the responsibility shift before mentioning declarative UI or Compose APIs.
- Explains the difference through **state and UI responsibility**, not XML versus Kotlin.
- Can show why manually coordinating several View mutations becomes harder as a screen gains more states.
- Understands that declarative UI means describing the UI for the current state, not "redrawing everything".
- Knows that Compose changes the rendering model; it does not decide where business state should live.
- Doesn't dismiss the View system. A well-structured View-based screen can still have clear state ownership and be perfectly maintainable.
- Stops there instead of turning a foundational comparison into a lecture about `remember`, recomposition internals, or Compose runtime APIs.

</SeniorAnswer>

## Key takeaways

<KeyTakeaways>

- The important difference is who keeps the UI synchronized with state.
- With Views, your code usually mutates existing UI objects when state changes.
- With Compose, you describe the UI for the current state and Compose applies the necessary updates.
- Compose changes who keeps the UI synchronized with state.
- Compose changes how the UI is rendered, not where application state should live.

</KeyTakeaways>
