<ShortAnswer>

`lateinit` and `lazy` both let you postpone initialization, but for different reasons.

With `lateinit`, you have a mutable property that will be assigned later, usually because the value only becomes available during setup, dependency injection, or a lifecycle callback. Kotlin trusts you to assign it before you read it.

With `lazy`, Kotlin has the code needed to create the value already. It simply waits until the property is accessed for the first time, creates it once, and then keeps that result.

So I think of `lateinit` as **assignment later**, and `lazy` as **creation on first access**.

</ShortAnswer>

## What the interviewer is testing

The syntax is straightforward. The useful distinction is whether initialization depends on **something happening later** or whether the object already knows **how to create itself when it is first needed**.

A strong answer also connects that decision to ownership and lifetime. `lateinit` makes sense when another phase of the object's lifecycle supplies the value. `lazy` makes sense when the owner can create the value itself and wants to defer that work until first use.

## ❌ Common mistake

<CommonMistake>

Avoid saying that `lateinit` and `lazy` are basically interchangeable because they both "delay initialization."

They delay it in different ways.

A `lateinit` property still needs an explicit assignment:

```kotlin
lateinit var repository: UserRepository

fun attach(repository: UserRepository) {
    this.repository = repository
}
```

A lazy property does not wait for an assignment. Its initializer runs when the property is first read:

```kotlin
val formatter by lazy {
    DateFormatter()
}
```

If you read a `lateinit` property before assigning it, you get an `UninitializedPropertyAccessException`. With `lazy`, the first read is what performs the initialization.

</CommonMistake>

## If they ask you to elaborate

### `lateinit` is assignment-driven

Sometimes an object cannot receive a useful value when the property is declared.

Android gives us plenty of examples: dependency injection may happen after construction, a view may only exist after a lifecycle callback, or test setup may provide a dependency before the test runs.

```kotlin
@Inject
lateinit var repository: UserRepository
```

The class is saying: **this value is required, but it will be supplied later**.

That is why `lateinit` works with `var`. The property starts without a value and is assigned later. It also cannot be used with nullable types or primitive types; the feature exists specifically for non-null reference properties that Kotlin would otherwise require you to initialize immediately.

### `lazy` is access-driven

With `lazy`, the owner already knows how to create the value:

```kotlin
private val adapter by lazy {
    UserAdapter()
}
```

Nothing else needs to assign `adapter`. The first access runs the initializer, and subsequent accesses return the same result.

That makes `lazy` useful when creating something immediately would be unnecessary work, or when the value should not exist until the code path that needs it is actually reached.

The important part is not "lazy is faster." The important part is that **initialization is tied to first access instead of to a separate setup step**.

<Remember>

**`lateinit` waits for an assignment. `lazy` waits for the first access.**

</Remember>

### Production considerations

The Android-specific trap is lifetime.

A lazy value is normally retained for as long as the object that owns the property is retained. That is fine for something whose lifetime matches the Activity, Fragment, ViewModel, or other owner. It is a poor fit for a value that needs to be cleared and recreated repeatedly.

Fragment ViewBinding is a good example. A Fragment instance can outlive its View, so keeping a binding for the whole Fragment lifetime can retain references to a destroyed View hierarchy. That is why the common Fragment pattern uses a nullable backing property that is cleared in `onDestroyView()` rather than a normal `lazy` binding that lives for the Fragment's entire lifetime.

```kotlin
private var _binding: FragmentProfileBinding? = null
private val binding get() = checkNotNull(_binding)

override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    _binding = FragmentProfileBinding.bind(view)
}

override fun onDestroyView() {
    _binding = null
    super.onDestroyView()
}
```

`lateinit` also deserves the same lifecycle thinking. If a property can legitimately become unavailable again, simply making it `lateinit` does not model that state. The declaration should match the lifetime of the thing it refers to, not just avoid a nullable type.

So the production question is not merely "which keyword is shorter?" It is **who supplies this value, when does it become valid, and how long should it remain valid?**

## Code example

Here are the two ideas side by side:

```kotlin
class ProfileActivity : AppCompatActivity() {

    @Inject
    lateinit var repository: ProfileRepository

    private val adapter by lazy {
        ProfileAdapter()
    }
}
```

`repository` is provided later by the injection process, so initialization happens through assignment. `adapter` can be created by the Activity itself, so initialization can wait until the property is first used.

The syntax is less important than the ownership difference: **one value is supplied; the other is created by its owner.**

## What separates a senior answer

<SeniorAnswer>

- Explains the difference as assignment-driven versus access-driven initialization instead of only listing `var` versus `val`.
- Connects `lateinit` to setup, injection, or lifecycle points where a required value becomes available later.
- Recognises that `lazy` owns its initializer and retains the first result rather than waiting for another part of the program to assign it.
- Thinks about lifetime before using either feature, especially when Android Views can be destroyed before their Fragment.
- Does not use `lateinit` merely to avoid modelling a genuinely optional or temporarily unavailable value.
- Does not describe `lazy` as a generic performance optimisation; deferring work is useful only when first-access initialization matches the ownership and lifetime of the value.
- Knows when the distinction has been explained and avoids turning the answer into a catalogue of delegation or thread-safety modes unless the interviewer asks for them.

</SeniorAnswer>

## Key takeaways

<KeyTakeaways>

- `lateinit` is for a non-null `var` that will be assigned after the object has been created.
- Reading a `lateinit` property before assignment throws `UninitializedPropertyAccessException`.
- `lazy` runs its initializer on first access and keeps the resulting value for later reads.
- `lateinit` is assignment-driven; `lazy` is access-driven.
- Choose based on ownership and lifetime, not simply because both avoid immediate initialization.
- On Android, make sure the property's lifetime matches the lifecycle of the object it references.

</KeyTakeaways>
